ColBERT: a vector for every token

ColBERT is a retriever that keeps a separate vector for every token of a passage. For each token of the query it finds the best match in the passage, and it adds up the scores of these matches to get the passage's score. All the passages' token vectors are built before any question arrives, so ColBERT stays fast. Khattab and Zaharia built it in 2020.

The need for it showed up at the end of lesson 12: a rare code like error 4012 gets lost in a passage's single vector. For the query error 4012, the answer is in a long FAQ, but a one-vector bi-encoder ranks a short, wrong passage above it. The cross-encoder from lesson 14 fixes this mistake, but it takes 10.7 ms per passage.

1One vector buries 4012

A bi-encoder squeezes a whole passage into one vector, and in a long passage one important token can get lost in that vector. Many bi-encoders build this vector by . In lesson 7 that meant adding up each number across all the token vectors and dividing by the number of tokens. For example, the average of [0.9, 0.1] and [0.7, 0.3] is [0.8, 0.2].

Now take the query error 4012, which has 2 tokens. Each token's vector has 3 numbers. The first says how much the token is about errors or uploads, the second how much it is about the code 4012, and the third how much it is about other topics. The query's tokens are error = [1, 0, 0] and 4012 = [0, 1, 0]. my vectors

The course's long FAQ covers grading, late days and Zoom, and one line gives the fix for error 4012. A short upload note only says that upload errors happen. A real FAQ would have hundreds of tokens, but here it has 6 to keep the arithmetic small.

The FAQ's average comes out number by number:

  1. First number: only error and 4012 have a first number other than 0. 0.9 + 0.1 = 1.0, and 1.0 ÷ 6 = 0.167.
  2. Second number: only 4012 has one, 0.95, and 0.95 ÷ 6 = 0.158.
  3. Third number: 1 from each of the four filler tokens, plus 0.1 from error, gives 4.1. Then 4.1 ÷ 6 = 0.683.

The third number is the largest, so the FAQ's vector points mostly towards other topics. Now take the from lesson 3, which is the dot product of two vectors divided by the product of their lengths. For example, the cosine of [1, 0] and [1, 1] is 1 ÷ (1 × 1.414) = 0.707. The query's average has a cosine of 0.32 with the FAQ's average, and 0.73 with the upload note's.

So the wrong upload note comes out on top, and the FAQ with the answer falls behind. The FAQ did contain 4012, but in the average it was only 1 token out of 6. Lesson 14 handled this situation with , bringing in BM25. ColBERT takes a different route: it never averages the tokens at all.

2MaxSim: the best match for each query token

ColBERT keeps a separate vector for every token of a passage, and a separate vector for every token of the query. These are the token vectors from lesson 7, where each token's vector is shaped by the words around it. The only difference is that ColBERT does not average them.

As with DPR in lesson 12, the document encoder builds these vectors and stores them in an , before any question arrives. When a question arrives, the query encoder builds vectors only for the query's tokens.

The score takes two steps. First, for each query token, take its with every passage token and keep the largest. Then add up these largest numbers over all the query's tokens. This score is called MaxSim.

3The cost: 100 times the vectors, but far less work

The price of keeping a vector per token is paid in the index: the number of vectors grows with tokens, not with passages. Suppose there are 60,000 passages with about 100 tokens each. A bi-encoder stores 60,000 vectors, and ColBERT stores 60,000 × 100 = 6 million, which is 100 times as many. The gap in bytes is smaller, because ColBERT's vectors are also smaller. my example

What we get in return is measured in two ways. The first is latency: the time from sending a query to getting the answer, in ms. For example, the cross-encoder from lesson 14 takes 10,700 ms for 1,000 passages, so its latency is 10,700 ms.

The second is the computer's work, counted in FLOPs: how many multiplications and additions it took. Our vectors have 3 numbers, so one dot product has 3 multiplications and 3 additions, which is 6 FLOPs. The FAQ's MaxSim had 2 × 6 = 12 dot products, so it took 12 × 6 = 72 FLOPs.

Stanford's slide measures ColBERT on MS MARCO. As lesson 14 showed, it holds real Bing search questions and 8.8 million passages. In the rerank rows, the model re-sorts BM25's top 1,000. is from lesson 13: one over the rank of the first correct passage, so rank 2 gives 0.5. The table writes it multiplied by 100.

T means trillion, 1012, and B means billion, 109. So 97T ÷ 7B = 97,000 ÷ 7 = about 13,900. So when reranking, ColBERT does about 13,900 times less work than the cross-encoder, with almost the same MRR@10: 34.9 against 34.7. Its latency is 61 ms instead of 10,700 ms.

The gap exists because the cross-encoder runs the whole of BERT on every passage. ColBERT runs BERT once on the query, and the passages' vectors are already built, so all that is left per passage is MaxSim.

In the end-to-end row, ColBERT does not rely on anyone else's list. It searches all 8.8 million passages itself, in 458 ms, with an MRR@10 of 36.0. The big gain is in the shortlist. tells you what share of the correct passages reached the top 1,000, so 1 out of 2 gives 0.5. ColBERT's Recall@1000 is 96.8, against 85.7 for BM25 (the one from a toolkit called Anserini), which is 11.1 points more.

4Cascade: the cheap step first, the precise step last

You now have four retrievers: BM25, DPR, ColBERT and the cross-encoder. Stanford's slide puts all four in one table:

Real systems put them in a line. The cheapest retriever pulls a long shortlist from the whole corpus, and each later step does more expensive, more precise work on fewer passages. This line is called a cascade. A cascade could look like this: my example

Each step's cost depends on the size of its list. ColBERT reranks 1,000 passages in about 61 ms. The cross-encoder takes 50 × 10.7 = 535 ms for 50 passages, while all 1,000 would have taken it 10,700 ms.

Each step relies on the previous step's shortlist, so the first step's recall is the ceiling for the whole cascade. This is the from lesson 14. If the right passage is not in the first step's list of 1,000, no later step can bring it back. That is why the first step uses both BM25 and DPR, with merging their lists.

Take an average instead of the max, and the wrong passage comes back

Instead of the max, we could take the average of each column. That is cheap too, and the paper tried it. from the paper On our numbers it works out like this:

  1. FAQ, error column: (0 + 0 + 0 + 0.9 + 0.1 + 0) ÷ 6 = 1.0 ÷ 6 = 0.167.
  2. FAQ, 4012 column: (0 + 0 + 0 + 0 + 0.95 + 0) ÷ 6 = 0.158. The FAQ's score is 0.167 + 0.158 = 0.325.
  3. Upload note: the error column gives (0.8 + 0.95 + 0.5) ÷ 3 = 0.75, and the 4012 column (0.1 + 0.05 + 0) ÷ 3 = 0.05. The score is 0.75 + 0.05 = 0.8.

The upload note is back on top with 0.8, and the FAQ is at 0.325. These numbers look familiar: 0.167 and 0.158 are the first two numbers of the FAQ's average vector, and 0.75 and 0.05 are the upload note's. That comes from a rule of the dot product: a · (b + c) = a · b + a · c. For example, [1, 0, 0] · ([0.9, 0, 0.1] + [0.1, 0.95, 0]) = [1, 0, 0] · [1.0, 0.95, 0.1] = 1.0, and computing the two separately also gives 0.9 + 0.1 = 1.0.

An average is just a sum followed by a division. So “dot products first, then their average” and “the average vector first, then one dot product” give the same number. Summed over both query tokens, this turns into the query's average vector as well:

∑i averagej (qi · dj) = 2 × (query's average) · (passage's average)

Here 2 is the number of query tokens. For the FAQ that is 2 × 0.1625 = 0.325, and for the upload note 2 × 0.4 = 0.8. The 0.1625 and 0.4 are exactly the dot products behind the cosines in step 1. Worked out in full, those cosines are:

  1. Length of the query's average [0.5, 0.5, 0]: √(0.5² + 0.5²) = √0.5 = 0.707.
  2. Length of the FAQ's average: √(0.167² + 0.158² + 0.683²) = √0.520 = 0.721. Cosine: 0.1625 ÷ (0.707 × 0.721) = 0.1625 ÷ 0.510 = 0.32.
  3. Length of the upload note's average: √(0.75² + 0.05² + 0.2²) = √0.605 = 0.778. Cosine: 0.4 ÷ (0.707 × 0.778) = 0.4 ÷ 0.550 = 0.73.

So an averaging MaxSim is really the one-vector method from step 1, only without dividing by the lengths. That is why the max matters: for each query token it picks a single passage token and removes the influence of all the others. In the paper's experiment, the averaging ColBERT also fell clearly behind, as step 6 shows.

The score's upper bound, and summing over query tokens

ColBERT brings every vector to length 1. from the paper To a vector, as in lesson 3, you divide each of its numbers by its length. For example, [3, 4] has length 5, so it becomes [0.6, 0.8]. The dot product of two vectors of length 1 is exactly their cosine, which stays between −1 and 1.

So each max is at most 1, and with 32 query vectors, S is at most 32. The paper gives every query exactly 32 vectors, as step 7 explains.

Our toy vectors do not have length exactly 1. For example, the FAQ's error [0.9, 0, 0.1] has length √(0.81 + 0 + 0.01) = √0.82 = 0.906. Normalized, it becomes [0.994, 0, 0.110]. Then MaxSim gives 1.99 for the FAQ and 1.12 for the upload note, so the order stays the same. my arithmetic

The formula sums over the query's tokens rather than averaging. An average would divide every score by the number of query tokens, for example 1.85 ÷ 2 = 0.925 for the FAQ and 1.05 ÷ 2 = 0.525 for the upload note. All passages for one query are divided by the same number, so the order does not change, just like the doubled vector in lesson 12.

7Inside ColBERT's encoders, and training

The slide shows two encoders, fQ and fD, but in the paper both are the same BERT. A special token [Q] is added in front of the query, and [D] in front of the passage. These tell BERT whose vectors it is building. from the paper

The query encoder runs in four steps: from the paper

  1. [CLS] and [Q] are added in front of the query's tokens. Then [mask] tokens fill the remaining space, so the query is 32 tokens long. A longer query keeps only its first 32 tokens.
  2. BERT builds a contextual vector of 768 numbers for each token.
  3. A linear layer turns each vector into 128 numbers.
  4. Each vector is normalized to length 1.

The passage encoder works the same way, except that it uses [D] instead of [Q] and adds no [mask] tokens. At the end it drops the vectors of punctuation such as commas and full stops, so each passage has fewer vectors.

Query augmentation: making the query longer with [mask] tokens

[mask] is a special BERT token with no word behind it. BERT still builds a vector for every [mask], and that vector is shaped by the query's real tokens. So these vectors take part in MaxSim like extra query tokens. The paper calls this query augmentation. In its words, it is a learned way to add new terms to the query or to re-weight the existing ones. from the paper

In the question in step 2, we added a third token, upload, to the query. Each passage's score then gained one more max: 0.9 for the FAQ and 0.95 for the upload note. Every [mask] vector adds one more max in the same way, except that BERT decides its vector. In the ablation of step 6, the model without it, [C], fell clearly behind.

The linear layer: from 768 numbers to 128

A linear layer is a multiplication by a . Each number of the result is the dot product of the input vector with one row of the matrix, exactly like the matrix-vector product in lesson 3. Here is a small version, from 3 numbers to 2, where the matrix's rows are [1, 0, 0.5] and [0, 1, 0.5]. my matrix On the FAQ's error [0.9, 0, 0.1]:

  1. First number: [1, 0, 0.5] · [0.9, 0, 0.1] = 0.9 + 0 + 0.05 = 0.95.
  2. Second number: [0, 1, 0.5] · [0.9, 0, 0.1] = 0 + 0 + 0.05 = 0.05.

The new vector is [0.95, 0.05], and it took 2 rows × 3 numbers = 6 multiplications. ColBERT's matrix has 128 rows of 768 numbers each, so every token takes 128 × 768 = 98,304 multiplications. Training learns the matrix's numbers. The paper chose 128 because smaller vectors shrink the index, and step 8 does that arithmetic. from the paper

Training: one right passage and one wrong passage

ColBERT trains much like lesson 12. Each example has three parts: a query q, a right passage d+ and a wrong passage d−. ColBERT computes the MaxSim of both and applies the softmax-then-−ln loss to them. This is the of lesson 12, with one negative. A batch holds 32 such examples. from the paper

With MaxSim scores 1.85 and 1.05, where the FAQ is the right passage and the upload note the wrong one, the loss works out like this:

  1. As in lesson 12, take for each score, where e is about 2.718: e1.85 = 6.36 and e1.05 = 2.86. They add up to 9.22.
  2. The FAQ's share: 6.36 ÷ 9.22 = 0.690.
  3. Loss: −ln 0.690 = 0.371. Check: e−0.371 = 0.690.

Late interaction has no parameters of its own, because max and sum learn nothing. Training changes only BERT, the linear layer and the vectors of [Q] and [D]. from the paper

8The cost in numbers: index bytes, FLOPs and 61 ms

Index bytes: vectors × numbers × bytes

An index's size is a product of three numbers: the number of vectors, the numbers per vector, and the bytes per number. In lesson 10 a typical number took 4 bytes, or 32 bits. The paper also tries 16-bit numbers, which take 2 bytes. from the paper For the 60,000 passages of step 3, with 4 bytes per number: my arithmetic

ItemBi-encoder, 768 numbersColBERT, 128 numbers
Vectors60,0006,000,000

There are 100 times as many vectors, but each vector is 768 ÷ 128 = 6 times smaller. So the gap in bytes is 100 ÷ 6 = about 16.7 times, and as a check, 3.07 GB ÷ 184 MB = 16.7. With 2-byte numbers, ColBERT's index halves to 1.54 GB. So the index grows in direct proportion to the number of tokens: twice the tokens, twice the bytes. Stanford's slide puts this as Index size: tokens, not documents.

Counting FLOPs: the query's BERT once, MaxSim on every passage

In step 3 we counted 72 FLOPs for the FAQ's MaxSim: 12 dot products, each with 3 multiplications and 3 additions. Real ColBERT follows the same count with bigger numbers: my arithmetic, assuming 68 vectors per passage on average

  1. 32 query vectors and about 68 passage vectors give 32 × 68 = 2,176 dot products.
  2. Each dot product has 128 multiplications, so 2,176 × 128 = 278,528 multiplications, and as many additions. That is about 0.56 million FLOPs per passage.
  3. For 1,000 passages, 0.56 million × 1,000 = 560 million FLOPs, about 0.56B.

The table lists 7B FLOPs for ColBERT in total, so MaxSim is a small part of it. The passages' vectors were built offline, so most of the rest is passing the query's 32 tokens through BERT. this split is my estimate

A cross-encoder spends 97T ÷ 1,000 = 97B FLOPs on a single passage, because it runs the whole of BERT on every passage. This arithmetic came up in the dense version of lesson 14.

The paper reports that this gap grows with k, the number of passages being reranked. At k = 10, BERT needs about 180 times ColBERT's FLOPs, at k = 1,000 it needs 13,900 times, and at k = 2,000 it needs 23,000 times. from the paper The reason works out like this: my arithmetic

  1. The cross-encoder does the same work for every passage, so at k = 10 it uses 10 × 97B = 970B FLOPs.
  2. ColBERT uses one 180th of that: 970B ÷ 180 = about 5.4B.
  3. At k = 1,000 ColBERT is at 7B, and 7 ÷ 5.4 = 1.3.

So with 100 times the passages, ColBERT's work grew only about 1.3 times, because the query's BERT runs once no matter what. Over the same range, the cross-encoder's work grew 100 times.

Where the 61 ms go

According to the paper, encoding the query and computing MaxSim take only 13 ms of ColBERT's 61 ms. The other 61 − 13 = 48 ms go into gathering the passages' vectors from memory and moving them to the GPU. These times were measured on one Tesla V100 GPU. 10,700 ÷ 61 = about 175, and the paper calls this more than 170 times faster. from the paper

Reranking ColBERT relies on BM25's list, so its full time includes BM25. Anserini's BM25 takes 62 ms on one CPU thread, so the total is 62 + 61 = 123 ms. The paper adds them the same way in its first chart. from the paper End-to-end ColBERT's 458 ms include no BM25 at all. They cover the two stages of step 9.

9End-to-end search: candidate passages first, then full MaxSim on them

A full MaxSim for each of 8.8 million passages is very expensive. The index holds about 600 million token vectors. With 32 query vectors, each query would take 32 × 600 million × 128 = about 2.5 trillion multiplications. my arithmetic So the paper searches in two stages, and both run on ColBERT's own vectors: from the paper

  1. Candidate generation: for each query vector, find the closest token vectors in the index. Each vector found belongs to some passage, and that passage becomes a candidate.
  2. Full MaxSim: compute the MaxSim of step 2 only for these candidate passages, and sort them.

This is a small cascade that runs inside ColBERT: the cheap stage first, and the full arithmetic last.

Add the Homework 1 announcement to our two passages. It has 3 tokens: homework [0.1, 0, 0.9], due [0, 0, 1] and friday [0, 0, 1]. Now the index holds 6 + 3 + 3 = 12 token vectors. my vectors In stage 1, each query vector brings back the 2 token vectors with the largest dot products:

Query vector2 closest token vectorsTheir passages
error [1, 0, 0]The upload note's errors (0.95), the FAQ's error (0.9)Upload note, FAQ
4012 [0, 1, 0]The FAQ's 4012 (0.95), the upload note's upload (0.1)FAQ, upload note

The candidates are the FAQ and the upload note. No token of the Homework announcement gives a dot product above 0.1 with any query token. So it never became a candidate, and its MaxSim was never computed. In stage 2 the FAQ gets 1.85 and the upload note 1.05, exactly as in step 2.

In this small example, stage 1 took 2 × 12 = 24 dot products and stage 2 took 2 × (6 + 3) = 18. Here stage 1 looks at every vector, so nothing was saved. In the real index, stage 1 does not look at every vector: from the paper

  • The paper keeps all token vectors in a faiss IVFPQ index, which is and from lesson 10 combined. The vectors are split into 2,000 clusters, and each query vector looks only at its 10 closest clusters.
  • Each vector is cut into 16 pieces, and each piece becomes a 1-byte code, so every vector is a 16-byte code.
  • Each query vector brings back its top 1,000 token vectors, so there are at most 32 × 1,000 = 32,000 passage IDs. A passage can appear more than once, so the real candidates are fewer.
  • Stage 2 computes full MaxSim on these candidates with the real 2-byte vectors.

If the clusters were equal in size, each query vector would look at 10 ÷ 2,000 = 0.5% of the vectors, about 3 million out of 600 million. Even for 32,000 candidates, stage 2 takes 32,000 × 278,528 = about 8.9 billion multiplications, about 280 times fewer than 2.5 trillion. my arithmetic Faiss runs on all CPU cores here, and the two stages together take 458 ms. from the paper

For end-to-end search the paper measures similarity with L2 distance instead of cosine, because its faiss index was faster with L2. That is why the table says ColBERTL2. from the paper is from lesson 10. For vectors of length 1, distance² = 2 − 2 × cosine, so both give the same order. Check: [1, 0] and [0.6, 0.8] have cosine 0.6, and distance² = 0.4² + 0.8² = 0.8 = 2 − 1.2.

Even so, the table has the L2 rerank at 34.8 and the cosine one at 34.9. My reading is that these are two separately trained models, and the L2 one stores each number in 2 bytes.

3 points from this lesson

  1. A one-vector bi-encoder can bury an important token of a long passage in the average. For error 4012, the FAQ's cosine was 0.32, and the wrong upload note's was 0.73. Taking an average instead of the max in MaxSim brings the same mistake back, 0.325 against 0.8.
  2. ColBERT keeps a 128-number vector of length 1 for every token. MaxSim adds up each query vector's largest dot product. The index grows with tokens: 286 GiB on MS MARCO, which by my count is about 600 million vectors.
  3. When reranking, ColBERT is as precise as a cross-encoder with about 13,900 times fewer FLOPs, because the query's BERT runs only once. End-to-end, candidate generation followed by full MaxSim lifts Recall@1000 to 96.8.

New terms in this lesson

Late interaction
The query's and the passage's token vectors are built separately, and meet only at scoring. For example, ColBERT builds passage vectors offline, and computes the dot products when the query arrives.
MaxSim
Each query token's largest dot product with the passage's tokens, then the sum of these. For example, 0.9 + 0.95 = 1.85 for the course FAQ.
ColBERT
A late-interaction retriever that keeps a vector per token and scores with MaxSim. Built by Khattab and Zaharia in 2020. For example, its Recall@1000 on MS MARCO is 96.8.
Latency
The time from sending a query to getting the answer, in ms. For example, the cross-encoder's latency is 10,700 ms for 1,000 passages, and ColBERT's reranking latency is 61 ms.
FLOPs
How many multiplications and additions it took, that is, the computer's work. For example, a dot product of 3 numbers takes 6 FLOPs, and one of 768 numbers takes 1,536.
Cascade
A line of retrievers in which each later step does more precise, more expensive work on fewer passages. For example, from tens of millions to 1,000, then 50, then 5.
Interaction matrix
A table of the similarity of every query token with every passage token. For example, the FAQ's table holds 6 × 2 = 12 dot products.
Query augmentation
Filling the query with [mask] tokens up to 32 tokens. BERT builds vectors for these too, and they join MaxSim like extra query tokens.
GiB
230 = 1,073,741,824 bytes, about 7% more than a GB. For example, ColBERT's MS MARCO index is 286 GiB.
Candidate generation
Picking candidate passages cheaply, so that the expensive arithmetic runs only on them. For example, in ColBERT each query vector brings back its top 1,000 token vectors, so at most 32,000 passages.
